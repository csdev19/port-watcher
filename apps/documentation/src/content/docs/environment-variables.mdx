# Environment Variables

## What the shipped app reads

Today the web app (the landing) reads exactly one variable, and it is optional:
`VITE_PUBLIC_DOWNLOAD_URL`, inlined at build time (production sets it from the `DOWNLOAD_BASE_URL`
GitHub variable; when empty both download buttons point at GitHub Releases). Everything else below
belongs to the server code that is currently disabled.

## How Env Vars Are Loaded (when the server code is enabled)

| App/Package                       | Method                                                                    | Source File                                                  | When                       |
| --------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------- |
| **fullstack-fn-only**             | Zod-validated `process.env` (`src/env/server.ts`, disabled)               | `apps/fullstack-fn-only/.env` (dev), wrangler secrets (prod) | Runtime (server functions) |
| **fullstack-fn-only** (client)    | Vite `import.meta.env`                                                    | `apps/fullstack-fn-only/.env`                                | Build-time                 |
| **infra-db** (drizzle migrations) | `dotenvx run -f apps/fullstack-fn-only/.env` from the root `db:*` scripts | `apps/fullstack-fn-only/.env`                                | Migration-time             |

Wrangler auto-loads `.env`, which is why `wrangler.jsonc` must never grow a `vars` block — it would
drift from that single source of truth.

## Variables by Context

| Variable                   | Server functions | Client                 | infra-db | Sensitive? |
| -------------------------- | ---------------- | ---------------------- | -------- | ---------- |
| `DATABASE_URL`             | Yes              | -                      | Yes      | **Yes**    |
| `BETTER_AUTH_SECRET`       | Yes              | -                      | -        | **Yes**    |
| `BETTER_AUTH_URL`          | Yes              | -                      | -        | No         |
| `VITE_PUBLIC_DOWNLOAD_URL` | -                | Yes (inlined at build) | -        | No         |

Auth and the database are currently **disabled** in the web app (see
`apps/fullstack-fn-only/vite.config.ts` and
[ADR 0005](https://github.com/csdev19/port-watcher/blob/main/docs/adr/0005-disable-web-auth-and-database.md)):
no shipped code reads `DATABASE_URL` or `BETTER_AUTH_*`, and production does not set them. The
rows for those variables describe the app once they are turned back on.

The schema that enforces this is `fullstackServerEnvSchema` in
`packages/infra-env/src/fullstack-server.ts`. Adding a variable means adding it there first —
the app fails fast at boot if it is missing. That check only runs when `src/env/server.ts` is
compiled, which it is not while the server code is disabled.

## Open item: encrypted secrets with dotenvx

Once re-enabled, `DATABASE_URL` and `BETTER_AUTH_SECRET` would live in plaintext in
`apps/fullstack-fn-only/.env`, which is gitignored and therefore shared out of band. [dotenvx](https://dotenvx.com) (AES-256 + secp256k1)
encrypts values inline so the `.env` file itself can be committed:

```bash
# before
DATABASE_URL=postgresql://user:pass@host/db

# after `dotenvx encrypt`
DOTENV_PUBLIC_KEY="03f98bf6e00bce..."
DATABASE_URL="encrypted:BCV9qZmblsUm77..."
```

The private key lives in `.env.keys`, which is never committed.

**Status:** this is a proposal for when the database returns; nothing here is needed to run the
landing. The root `db:*` scripts already invoke `dotenvx run -f apps/fullstack-fn-only/.env`, but
`@dotenvx/dotenvx` is not yet a dependency of this repo and no file is encrypted. Adopting it means:

1. Add `@dotenvx/dotenvx` as a root devDependency.
2. `dotenvx encrypt` the app `.env`.
3. Add `.env.keys` to `.gitignore`.
4. Store `DOTENV_PRIVATE_KEY` in a password manager and as a CI secret.
5. Optionally wire `dotenvx ext precommit` into `lefthook.yml` so an unencrypted secret cannot be
   committed.

Deployment secrets are managed as GitHub Actions secrets today and need no change.
